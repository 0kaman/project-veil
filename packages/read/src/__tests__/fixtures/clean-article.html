Understanding HTTP

By A. Writer

The Hypertext Transfer Protocol is the foundation of data communication on the web. Every time a browser requests a page, it speaks HTTP to a server, and the server answers in the same language. This exchange is deceptively simple and endlessly deep.

Requests and responses

An HTTP request carries a method, a path, headers, and sometimes a body. The method tells the server what the client wants: GET to retrieve, POST to submit, PUT to replace, DELETE to remove. The path names the resource. Headers carry everything else, from the accepted content types to the authentication tokens.

A response mirrors that shape. It opens with a status line, a three digit code that summarises the outcome, then its own headers, then the body. A two hundred means success. A four oh four means the resource was not found. A five hundred means the server broke.

Statelessness

HTTP is stateless by design. Each request stands alone, carrying no memory of the requests before it. This makes servers simpler and more scalable, but it means that anything resembling a session must be reconstructed on every request, usually from a cookie the client presents each time.

That single constraint shapes an enormous amount of web architecture. Load balancers can route any request to any server precisely because no server holds special knowledge of a client. The cost is paid in cookies, tokens, and the constant re-establishment of who you are.

Encryption

Plain HTTP travels in the clear, readable by anyone on the path. HTTPS wraps it in TLS, negotiating a shared secret before any request is sent. The negotiation itself reveals nothing useful to an eavesdropper, and once complete, every byte is encrypted end to end.
