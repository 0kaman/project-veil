| 2026-07-15 | **FIXED: settle ignores long-lived connections — google 14.1s → 4.1s.** `whenQuiet` no longer requires `pending === 0`. In-flight requests are now keyed **id → startedAt** (page-side `inflight` object; host-side `Map<requestId, startedAt>`) instead of a bare counter, and only requests younger than `VEIL_LONGPOLL_MS` (default **2000**) block settle. A connection open longer than that is a persistent one (long-poll / SSE-over-XHR / keepalive) that will never close — waiting on it is what turned the event-driven settle into a flat cap-length timeout. Safe because late-arriving data still reaches the graph via the MutationWatcher's incremental-update path, so settling early loses nothing permanently. Applied to **both** paths (page-side `whenQuiet` **and** the strict-CSP `hostQuiescence` fallback, which had the identical `inflight <= 0` flaw). `awaitQuiescence` now **surfaces** `reason:'cap'` via `debugLog` (with young/total in flight) instead of discarding the verdict — the reason this hid for so long. Settle env vars are read **per call**, not bound at module load, so a host loading its `.env` after importing `@veil/core` gets the configured values (and so this is testable without a subprocess). **Measured after:** google.com 14,090→**4,080ms**, `/search?q=…` 17.7s→**4,943ms**, all now `settle=quiet`; example 2.3s / github-login 2.8s / HN 2.9s unchanged (they already went quiet); node counts identical (search 139, HN 479) — no perception lost. **Tests:** Layer 2 `integration/longpoll.integration.test.ts` + `fixtures/longpoll.html` + a `/hang` route that sends headers and never ends — (a) settles promptly, (b) **still waits for a young in-flight request** (asserts the click's `POST /api/send` edge has `response.status === 200`; the guard against trading a latency bug for a correctness bug), (c) burns the cap when `VEIL_LONGPOLL_MS` is disabled, proving the test is load-bearing. Layer 1 `quiescence.test.ts` gains a hermetic long-poll case. NOTE: the pre-existing Layer-1 fakes emitted `Network.requestWillBeSent` with `{}` — real CDP **always** sends `requestId`; the fakes were made realistic (assertions unchanged), and a missing `requestId` now warns under `VEIL_DEBUG` rather than silently un-blocking settle. | `browser/instrumentation.ts` (`whenQuiet`), `browser/page.ts` (`awaitQuiescence`, `hostQuiescence`) |
| 2026-07-15 | **ROOT CAUSE: `veil_open` on google.com costs 14.1s — of which the pipeline is 211ms.** The other ~14s is `awaitQuiescence` burning `VEIL_QUIESCE_CAP_MS` (12s) in full. `whenQuiet` requires `domQuiet && reqQuiet` where `reqQuiet = pending <= 0`; google's DOM is provably silent (0 mutations measured), but `pending` is pinned at **1 forever** by a long-lived autocomplete XHR (`/complete/s?q&cp=0&client=gws-wiz`) that never fires `loadend`. Given 45s it still never resolves (CDP timed out at 30s first). **Evidence:** (a) cap 12000→2000 moved open 14,090ms→4,719ms, a ~1:1 trade proving the cap is fully burned; (b) the page's own `whenQuiet` returns `{reason:'cap',pending:1}` on every attempt; (c) Chrome's Network domain reports **0** requests in flight — so it is Veil's counter, not real traffic. **Not a Google quirk — architectural:** requiring zero in-flight fetch/XHR is unattainable on any page holding a persistent connection (long-poll, SSE-over-XHR, chat, dashboards), so the "event-driven settle" silently degrades to a flat 12s-per-action floor — the exact "fixed-time floor" the 2026-07-13 row claims to have removed (true only for pages that do go quiet). **Invisible because** `page.ts` `awaitQuiescence` does `if (res.result.value != null) return`, discarding `{reason:'cap',pending}` — cap and genuine quiet are indistinguishable to the caller even under `VEIL_DEBUG=1`. Measured: example 2.4s / github-login 3.3s / HN 2.8s / MDN 3.1s all settle `quiet`; google 14.2s `cap`. (Wikipedia's ~21s is a *separate* issue — it settles `quiet`; the page is genuinely heavy.) **Proposed fix (not yet applied):** drop the `pending===0` requirement — track in-flight requests with start timestamps and count only *young* ones (a request open >~2s is a persistent connection by definition), and surface `reason:'cap'` under `VEIL_DEBUG`. | `browser/instrumentation.ts` (`whenQuiet`), `browser/page.ts` (`awaitQuiescence`) |
| 2026-07-15 | **Episodic log + cross-session analysis for the playground.** Each session appends one distilled `Episode` to `traces/episodes.jsonl` (turns w/ outcome+tokens, per-tool p50/p95/max **plus every raw duration**, pages visited w/ node+token counts, auto-detected anomalies); `pnpm play:analyse` aggregates across every episode. Recorder is just another `Tracer` subscriber (the UI is a view; this is a memory), flushed via `process.on("exit")` so a crash still records. **Timeout detection requires TWO conditions:** a duration constant *per page* (±8%; work varies, caps don't) **AND** ≥ 0.9 × the configured settle cap. Both are needed — two weaker heuristics were tried and **rejected against real data**: (1) *"any constant ≥3s"* flags ordinary load times (google post-fix is reliably ~4.5s — that's just google); (2) *"the same constant across different pages"*, which sounds far more compelling and was the story originally told about how the bug was found, is actually **birthday-paradox noise** — on a diverse corpus it flagged **5 innocent clusters and missed the real bug**, which only ever hit google (the google-14.9s/wikipedia-15.2s "agreement" was a coincidence; wikipedia settles `quiet` and is merely heavy). A settle that times out costs cap + load, so proximity to the cap is the real fingerprint. Final detector verified both ways: on pre-fix episodes it flags `veil_open @ google.com ~14.5s ×2 ⇒ ≈ the 12.0s cap`; on post-fix episodes it reports `none` and files google's 4.5s as benign — 1 true positive, 0 false positives. Also: episode `totals.activeMs` (sum of turn durations), **not** session lifetime — a REPL left open recorded a 17-hour `ms` that swamped every aggregate. Raw durations are kept per episode so analysis can re-cluster later. | `packages/playground/src/episode.ts`, `src/analyse.ts` |

Step-gated by default (the model picks a tool; the call is held until a keypress — verified holding a call 12.3s), `--auto` for unattended. Everything fans out to a typed trace bus → Ink UI + append-only `traces/<ts>.trace.jsonl`: LLM latency + **real** token usage, per-tool latency/size/errors, `graph.observed` (node count, section counts, node ids added/removed vs previous), Veil's own stderr via `VEIL_DEBUG=1`, and named detectors (`REPEATED_CALL`, `BAD_TOOL_ARGS`, tool error codes). Parses the compact text rather than reading the graph object, because that text IS the model's whole perception; any gap between it and the graph is the bug class we're hunting. | 2026-07-14 | **Direct-API execution tier — replay captured requests instead of re-simulating.** `page.replay(node, edits)` parameterizes a captured template (JSON deep-merge / form-urlencoded / query / headers via pure `applyEdits`) and fires it through the page's own fetch (inherits cookies/session/CSRF); returns the API response, NOT a rebuilt graph (a raw request changes server state + returns data, it does not drive the app's DOM). `canReplay()`, two-tier `execute(mode: auto/direct/simulate)` (auto = direct when a template exists else simulated interaction), MCP `veil_replay` tool. `interact()` unchanged → no regression. **BENCHMARK (median, add-to-cart):** instant API — simulated **121ms** vs direct **1ms** (**121×**, batch-of-50 6.0s→0.1s); 200ms API — simulated **283ms** vs direct **204ms** (**1.4×**, saves the ~80ms fixed overhead per action, batch-of-50 14.2s→10.2s). ## Open / scoped future work

- **OOPIF / cross-origin iframe capture.** Out-of-process frames (ads, OAuth
  popups, embedded checkout) are invisible today. Plan: `Target.setAutoAttach
  {flatten:true}` on the browser target → attach a `PageHandle`-like session per
  child frame → run Stages 1–3 per frame → merge into the parent graph under a
  frame-namespaced id prefix (`frame1:node-…`) so display ids stay unique. Deferred
  as a larger, riskier change; wanted to land the crash/correctness/MCP work first.
- **Stealth hardening** (canvas/WebGL/font spoofing) — only if a real target needs it.
- **Multilingual semantics** — via the enricher, not more regex.
- **Request-shape persistence across incremental updates** — request bodies aren't
  persisted on edges, so `requestShape` can go stale after an incremental rebuild.
- **`networkEdges` cap** on very long-lived analytics-heavy pages (unmatched edges
  aren't pruned).
- ~~Large content pages~~ **FIXED (2026-07-12).** Live real-site testing found
  two failures on content-dense pages; both fixed:
  - **Navigation timeout → soft-fail + configurable.** `navigate()` no longer
    throws when the load event is slow; it builds a PARTIAL graph from what's
    loaded (a partial perception beats a hard failure) and logs it. Default raised
    30s → 45s, configurable via `VEIL_NAV_TIMEOUT_MS`. The Wikipedia Cat article,
    which used to time out, now builds.
  - **Node budget prune** (`pipeline/prune.ts`). After events/semantics are known,
    an iterative pass drops the lowest-value leaves (plain content/nav links with
    no behavioral handler), deepest-first, collapsing bulk-link subtrees — never a
    form control, button, container, or event-bearing node. Budget `VEIL_MAX_NODES`
    (default 800, 0 = unlimited); `metadata.nodesTrimmed` records the count so a
    capped graph never looks complete. Results: Wikipedia HTTP 1,828 → 800,
    Cat ~4,173 → 1,067 (all 25 buttons preserved), app pages unchanged
    (github.com/login: 30, trimmed 0). Encyclopedia articles may still exceed the
    budget when structural containers dominate — the prune is safe best-effort.
  Live smoke tests: `integration/live-sites.integration.test.ts` (`VEIL_LIVE=1`).
