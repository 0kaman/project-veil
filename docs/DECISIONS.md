## The reboot

| date | decision | why | where |
|---|---|---|---|
| 2026-07-15 | **A browser is a fallback, not a foundation. Every task starts as HTTP.** Booting Chrome costs **969MB, 8 processes and 2,116ms** before one byte is read, and caps concurrency at ~10 sessions. You need it for exactly two things: the bytes don't exist until JS runs, or the server refuses non-browsers. Everything else is ~32× cheaper without it. So the engine is summoned, never assumed. | This is the move Dia/Comet/Atlas **structurally cannot make** — a human is watching their pages, so they must render everything, always. Veil has no viewport. Declining to boot is the payoff of the AI-first bet, and it's larger than the token efficiency we originally claimed for it. | [[ARCHITECTURE]] "The one idea" |
| 2026-07-15 | **Search is an API, never the browser.** Brave. The headless-search path is deleted, not kept as a fallback. | Measured: `veil_open` on a Google SERP took **11,622ms**; the API takes ~200ms — **58×**. And the browser path is unwinnable: fetched with no browser, **Google returns a JS stub, DuckDuckGo a CAPTCHA ("select all squares containing a duck"), Bing a CAPTCHA**. Fighting that is an arms race against companies with more engineers than we will ever have, to perform a GET. | `@veil/search` |
| 2026-07-15 | **Brave free tier: 1 query/sec, 2,000/month. `extra_snippets` unavailable — and silently ignored.** Cache searches aggressively; they cannot be parallelised. Project the response before returning it. | Measured on the real key: `x-ratelimit-limit: 1, 2000`. `extra_snippets=1` returns **HTTP 200 with zero snippets** — no error, no warning. Had we built assuming it worked, we'd have shipped a system that quietly got less than it thought. Raw JSON is 26KB (**~6,709 tokens**) for 10 results; the useful projection is **~900**. 2,000/month ≈ 66/day is a dev budget — mock search in tests. | `@veil/search` |
| 2026-07-15 | **Read path: fetch → parse5 → readability. No browser.** Escalate to the engine on exactly two triggers — **JS shell** or **doorman** — never on a guess. The fetch itself is the test. | Measured, same page both ways: **fetch 490ms + parse 48ms + extract 89ms = 627ms**, yielding 7,867 words of actual article. Through the engine: **20,871ms**, 800 nodes, **zero paragraphs**. 32× slower to get strictly less. The zapier post is 2,253 words (~3k tokens) via fetch; v1's graph of the same page was **11,355 tokens containing share buttons and no prose**. | `@veil/read` |
| 2026-07-15 | **Word count is the extraction signal. Discard ratio is noise.** | An invented metric ("91% discarded · confident") died on contact with data: a real article discards **98.0%**, a marketing page **94.9%** — the ratio tracks boilerplate, not success. Word count separates cleanly: real articles **2,253 / 7,867**; JS stub **0**, app **10**, marketing **97 / 485**. Second heuristic of mine to die this way (see the timeout-cluster row) — hence the receipt rule. | `@veil/read` |
| 2026-07-15 | **Read budget: 4,000 words + outline + handle.** Beyond it, return an outline and `veil_read(handle, query)` to pull. No separate grep verb. | Chosen from real samples so typical pages arrive **whole** (zapier 2,253 ✓, browseros 485 ✓) and only long-form is cut (wikipedia 7,867 → 51%). Fixing *what* you read doesn't fix *how much*: 7 Wikipedia-sized pages is ~90k tokens — the same context death with better material. The outline costs ~80 tokens and tells the model precisely what it's missing. | `@veil/read` |
| 2026-07-15 | **Handle, not payload — on all three surfaces.** search 6,709→~900 tok · read 10k→4k+outline · open 18k→~200 tok + summary. Data stays host-side; the model gets a reference. | The model's context is the scarce resource. v1 shipped **43,736 tokens across 7 pages and used zero of them**; the final call was **58,201 tokens and took 73.8 seconds**. That it independently applies to all three surfaces is how we know it's the real principle and not a patch. | all |
| 2026-07-15 | **The receipt: no silent degradation.** Every response declares path, cost, and what it does **not** have — including `BLOCKED both ways`. | **Every failure in v1 was silence, not slowness.** `awaitQuiescence` discarded `reason:'cap'` → a 12s stall hid for months. `prune` set `nodesTrimmed` and the compact text never printed it → asked whether a capped graph was complete, the model answered *"792 nodes and truncated"*: the count hallucinated, the verdict a guess. Stage 1 dropped every paragraph and said nothing → the model summarised 7 pages it had never read and cited *"job postings"*. A tool that fails is fine; a tool that fails quietly makes the model lie. | all |
| 2026-07-15 | **The graph stays pure behaviour. Prose only ever comes from `veil_read`.** Reverses an earlier call in the same session to un-drop `StaticText` in Stage 1. | One artifact, one job. The AX tree *does* carry the prose (`StaticText:18`, `paragraph:2` on github/login — Chrome computed it, Stage 1 filtered it) so un-dropping was tempting and cheap. But with a read path it's the wrong seam: it would put two jobs back in one machine, which is the exact fault we rebooted to fix. Cost accepted: a page that is both article and app needs two calls. | `@veil/core` Stage 1 |
| 2026-07-15 | **Six verbs. The surface is the router.** `search · read · open · query · do · replay`. Descriptions written as signposts (`read` = "use this first"; `open` = "boots a browser — only to act"). | No classifier, no intent model — the LLM picks, which is the one thing LLMs are reliably good at. v1 shipped 8 tools and the model **never once** called `veil_query`, because `veil_open` had already handed it everything. The verb wasn't the bug; the payload was. | `@veil/mcp` |
| 2026-07-15 | **One cookie jar, shared by fetch and engine.** | Unlocks the flywheel: `veil_auth` once with the browser, and every later fetch is authenticated and cheap (~630ms instead of ~4s). Two transports with separate session state is miserable to retrofit, so it's decided before any code exists. | `@veil/core`, `@veil/read` |
| 2026-07-15 | **Learn once, then replay. Replay is downstream of interaction, not an alternative to it.** | You cannot replay a request you have never observed: `veil_do` fires it once and teaches the cache; `veil_replay` then fires it directly forever — **121×** on v1's benchmark. Honest limit, carried from v1: a raw request changes server state but does **not** drive the DOM, so it wins on repeats/batches/data and breaks on novel multi-step flows where step 2 depends on step 1's DOM. | `@veil/core` |
| 2026-07-15 | **`@veil/read` owns the dependencies; `@veil/core` stays zero-dep.** parse5 + linkedom + @mozilla/readability. | The zero-dep rule survives by **not applying** to the new package rather than by being broken. Measured cost: **15 transitive packages, 7.2MB, 137ms** on a 589KB page — the libraries are noise, the fetch dominates. Hand-rolling an HTML parser is a multi-year bug farm; HTML's error-recovery spec exists because real pages are broken. **But Readability has opinions and fails silently** (it discards ~91–98% by text/link density) — which is why extraction confidence is a receipt field, not a footnote. Core stays small and auditable: it's the part holding the cookies. | `@veil/read` |
| 2026-07-15 | **Politeness: 10 global / 2 per-host concurrent, ~300ms spacing, 10s timeout, 1 retry on 429/503, real Chrome UA.** | Ten search results are usually ten domains, so per-host rarely binds — it's the brake for when a task hammers one site. **The tension, named:** politeness says identify as a bot, access says look like Chrome; you cannot do both. Veil fetches pages a user explicitly asked for — browser-equivalent, not crawling — so: real UA, and behave well. Strict `robots.txt` belongs to the crawler. | `@veil/read` |
| 2026-07-15 | **Crawler parked, not cancelled.** Crawl a site → map its API surface → expose it for direct calls. | Strategically the strongest idea on the table and the natural extension of Stage 3 + replay: it would turn the browser from a per-task cost into a **per-site, one-time** cost, and nobody else is near it. Parked because the runtime has to exist first, and because it has real constraints to design for: **coverage is partial by construction** (crawling surfaces GETs; the POST behind a validated form never fires), API discovery *requires* the engine (~4s + 969MB per page, so a 1,000-page site is over an hour and needs bounds), and one sighting of an endpoint is not a schema. | — |

## Post-mortem: what v1 measured (code at `9e9f3e0`)

| finding | evidence |
|---|---|
| **The pipeline was never slow.** | Full decomposition of google.com: **211ms**. The other ~14s was `awaitQuiescence` burning its cap. |
| **Settle required `pending === 0`, which real sites never reach.** | Google's autocomplete XHR (`/complete/s`) never fires `loadend` → counter pinned at 1 → every action burned the full 12s cap. Fixed for the network half (`VEIL_LONGPOLL_MS`, id-keyed in-flight tracking): google.com **14,090 → 4,080ms**. The **DOM half still fires** — `domQuiet` is unreachable on animated pages (diabrowser.com: 17.8s with *zero* requests in flight). "Wait for quiet" is the wrong model, not a wrong constant. |
| **The behaviour graph is excellent for acting and blind for reading.** | github/login: **30 nodes, 1,013 tokens**, with `POST /session` attached — nothing else gives an agent that. wikipedia/HTTP: **800 nodes (capped), 18k tokens, 18% behavioural**. zapier article: **405 nodes, 0 prose**; the longest string in 11,355 tokens was the author's bio, harvested from a link's accessible name. |
| **The agent contributed the nouns; the model's weights contributed everything else.** | Across 7 pages the graphs named Dia/Comet/Atlas/Fellou/Genspark/BrowserOS (all present as link text). **"Chromium" — the load-bearing claim of the whole answer — appears 0 times in the pages and 17 times in the answer.** The browser delivered ~7 proper nouns for 104.3s and 43,736 tokens. |
| **CDP is exonerated.** | It ran thousands of AX/listener queries in 211ms, and it was the instrument that caught every bug — `Network.requestWillBeSent` proved Chrome had **0 requests in flight** while Veil's counter said 1. The friction was never the protocol; it was booting a browser for jobs that didn't need one. |
| **A browser is a credential, not just an engine.** | Measured JA3/JA4 on the same machine, seconds apart: curl `375c6162…` / `t13d4907h2` (49 ciphers, 7 extensions) vs Chrome `aa99bba3…` / `t13d1516h2` (15 ciphers, 16 extensions). The TLS ClientHello decides it **before a single HTTP byte**; header spoofing cannot touch it. Headless Chrome's JA3 is identical to headed Chrome's — which is exactly why booting it gets through the door and curl gets a CAPTCHA. |

## Open / scoped future work

- **The DOM half of the settle cap.** Still 12s per action on animated pages. Needs
  a different model (perceive immediately, update incrementally), not a bigger cap.
- **The doorman beats headless too.** Cloudflare fingerprints headless Chrome.
  Veil says `BLOCKED both ways` and stops. Stealth is not a workstream until it
  must be — but note v1's disguise was *actively broken*: UA claimed Chrome 131 on
  a 150 binary (and `Sec-CH-UA`, which `--user-agent` does not override, reported
  the real 150 — a self-contradiction no real browser produces), and
  `--disable-gpu` removed WebGL entirely, which no real Mac Chrome does. Layers
  3–4 are why you need a browser; layers 5–7 are where v1 threw that away.
- **CDP vs WebDriver BiDi.** Portability and a real standard, against capability —
  BiDi has no async initiator stacks today, and those are what make Stage 3 (the
  moat) possible. Staying on CDP; worth an argument, not a default.
- **Cross-origin iframes (OOPIF)** — `Target.setAutoAttach` + per-frame sessions +
  frame-namespaced ids. Designed in v1, never built.
- **The crawler** — see the row above.
